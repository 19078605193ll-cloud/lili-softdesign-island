# AI 回答长时间等待排查（2026-10-02）

## 原因与证据

本机 `http://127.0.0.1:8000/h5/` 最近三条失败教学任务的错误均为
`APITimeoutError`。Worker 已领取任务，每次模型调用约 120 秒后超时，
自动重试一次，总等待约四分钟。Celery 的 `Task succeeded` 仅表示执行函数
正常返回；业务失败已写入 PostgreSQL `jobs`，不能据此判断模型回答成功。

在相同 worker 容器、供应商 URL 和密钥下做最短请求对照：

| 请求 | 结果 |
| --- | --- |
| `/models` | HTTP 200，1.06 秒 |
| `gpt-5.6-luna`，非流式 | 25 秒探测超时；原业务请求 120 秒超时 |
| `gpt-5.6-luna`，流式 | 35 秒探测超时 |
| `gpt-5.4-mini` | HTTP 200，2.28 秒，返回 OK |
| `gpt-4.1-mini` | HTTP 200，3.12 秒，返回 OK |

故障定位到 DMXAPI 的 `gpt-5.6-luna` 调用路径。无法仅凭这些数据区分
供应商内部排队和其上游故障，但不是普遍的容器断网、密钥失效或队列未执行。

## 已实施

- 本机 `.env` 的 `AI_TUTOR_MODEL` 改为 `gpt-5.4-mini`，重新创建 API、worker、dispatcher。
- 教学请求读取 `AI_TIMEOUT_SECONDS`，修复此前固定为 120 秒而忽略配置的问题；本机仍为 120 秒。
- UI 区分排队、思考、自动重试；失败显示 AI 超时或服务不可用提示。
- 任务失败日志记录任务 ID、异常类型、状态和重试次数，不记录密钥、用户消息或供应商响应正文。
- 重新构建本地应用镜像并更新运行容器，使前端提示也生效。

现有失败任务保留记录，不批量重新投递。第 47 题已通过页面“重试”恢复。

## 验证

- 原第 47 题点击重试：真实模型执行约 9.1 秒，回答保存成功。
- Chromium 真实追问：8.6 秒；WebKit 真实追问：6.6 秒。
- 两浏览器均观察到排队、运行、成功状态；刷新后回答一致，无页面异常或失败 API 请求。
- 检查 390px 和 1280px 宽度，无横向页面溢出；公式正常显示。
- 前端构建及 20 项单测通过。
- 后端 11 项相关测试通过，包含配置超时、自动重试一次、最终失败、手动重试恢复。
- 浏览器全流程覆盖登录、作答、追问、图表、类似题、刷新恢复、错题本和移动布局。
  全套运行中发现公式组件测试需要 Vite，而原配置将其发往 API 的 SPA；
  已为组件测试配置独立 Vite 服务，保留业务测试使用隔离 API。
  修正后 Chromium/WebKit 共 10 项 Playwright 测试全部通过（隔离测试入口 58.9 秒）。

真实浏览器报告和截图：`var/h5-acceptance/ai-timeout/`。
隔离浏览器测试运行日志：`.local-runtime/ai-e2e.log`。
本次验证覆盖本机环境和测试时刻，不代表供应商未来不会再次超时。

## 再次出现时

先检查 `jobs.error_code` 和 worker 日志，区分排队、模型超时、鉴权及限流。
使用相同容器和最短消息对照当前模型与已知可用模型，避免只增加等待时间。
调整 `.env` 后执行：

```powershell
docker compose -f compose.local.yml -p softdesign-island-app up -d --force-recreate api worker dispatcher
```

仅执行 `restart` 不会加载新环境变量。模型恢复后可在页面点击“重试”。
